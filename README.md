# 🎬 ReelTariler — 최신 영화 · OTT 트레일러 탐색 서비스

단순한 영화 검색 페이지가 아니라, **외부 API 연동 · 반응형 UI · 영상 재생 흐름을 직접 설계한 프론트엔드 프로젝트**입니다.

> "화면을 그리는 것"이 아니라
> **"데이터를 어떻게 안전하고 매끄럽게 화면까지 연결할지"**를 고민하며 개발했습니다.

---

## 📌 프로젝트 개요

ReelTariler(Reel + Trailer)는 다음 두 가지를 동시에 만족시키는 것을 목표로 설계했습니다.

### 1. 콘텐츠 탐색 경험

- 최신 영화 / OTT 오리지널 프로그램을 한 곳에서 탐색
- 카테고리별 캐러셀로 콘텐츠를 빠르게 훑어보고, 클릭 한 번으로 트레일러 재생

### 2. 안전한 외부 API 연동

- 클라이언트에 API 키가 노출되지 않도록 프록시 서버를 경유
- 응답 데이터를 화면에 맞게 가공하는 로직을 컴포넌트와 분리

---

## ✨ 주요 기능

### 🔍 콘텐츠 탐색

- 최신 영화 / OTT 프로그램 목록 조회
- 카테고리·장르별 캐러셀 UI
- 상세 정보 모달 (줄거리, 개봉일, 장르 등)

- 유튜브 기반 예고편 재생 (react-youtube / react-player)

### 📱 반응형 UI

- 모바일 / 데스크탑 환경 모두 대응하는 레이아웃

# 🧠 핵심 설계 및 의사결정

---

## 1. API 키 보호를 위한 프록시 구조

### 선택

- CRA 기본 fetch 대신 `http-proxy-middleware`로 개발 서버 단에서 외부 API 요청을 프록시 처리

### 이유

- 클라이언트 번들에 API 키가 그대로 노출되는 것을 방지
- 요청 도메인을 프록시가 감싸면서 CORS 이슈 회피

### 트레이드오프

| 방식                 | 장점               | 단점                                 |
| -------------------- | ------------------ | ------------------------------------ |
| 클라이언트 직접 호출 | 구현 단순          | API 키 노출, CORS 문제               |
| 프록시 미들웨어      | 키 은닉, CORS 회피 | 프로덕션 배포 시 별도 서버/설정 필요 |

→ 개발 단계의 보안을 우선했지만, **정적 호스팅 환경(예: Vercel/Netlify)에서는 프록시가 동작하지 않는 한계**가 있어 실제 배포 시 별도 서버리스 함수가 필요했습니다.

---

## 2. 상세 정보 UX: 모달 vs 별도 페이지

### 선택

- 목록에서의 상세 조회는 `react-modal` 기반 모달로 구현

### 이유

- 목록 탐색 흐름을 끊지 않고 빠르게 정보를 확인할 수 있도록 함
- 라우팅 이동 없이 배경 목록 스크롤 위치 유지

### 트레이드오프

- URL에 상태가 반영되지 않아 특정 콘텐츠 상세를 **링크로 공유할 수 없음**
- 뒤로가기 시 브라우저 히스토리와 모달 상태가 자연스럽게 연동되지 않는 한계

→ 이 부분은 이후 Next.js 마이그레이션에서 **라우팅 기반 모달(Intercepting Route)** 구조로 개선을 계획하고 있습니다.

---

## 3. 캐러셀 및 영상 재생 컴포넌트 분리

### 선택

- `react-slick`으로 카테고리별 캐러셀 구현
- 트레일러 재생은 `react-youtube`/`react-player`를 모달 내부 컴포넌트로 분리

### 이유

- DOM/window에 직접 의존하는 라이브러리이므로 재사용 가능한 단위로 캡슐화
- 캐러셀 옵션(자동 재생, 반응형 breakpoint)을 컴포넌트 props로 제어 가능하도록 설계

### 트레이드오프

- 무거운 서드파티 라이브러리 의존으로 번들 사이즈 증가
- CRA 특성상 코드 스플리팅이 세밀하게 적용되지 않아 초기 로딩에 영향

---

## 4. 스타일링: MUI + styled-components 혼용

### 선택

- 레이아웃/공통 컴포넌트는 MUI, 세부 커스텀 스타일은 styled-components로 분리

### 이유

- MUI로 빠르게 기본 UI를 구성하고, 디자인이 세밀하게 필요한 영역만 직접 스타일링

### 트레이드오프

- 두 스타일링 방식이 혼재되며 런타임 스타일 계산 비용이 이중으로 발생
- 팀 협업 시 스타일 작성 기준이 모호해질 수 있음

→ 유지보수성과 성능 측면에서 **단일 스타일링 전략(Tailwind 등)으로 통일할 필요성**을 느낀 부분입니다.

## 5. 프로젝트 구조

```
src/
├── components/     # 공통 UI 컴포넌트 (카드, 모달, 캐러셀 등)
├── pages/          # 라우트 단위 페이지
├── api/            # 외부 API 요청 로직
├── hooks/          # 커스텀 훅
├── styles/         # 전역 스타일, 테마
└── App.js
```

## ⚡ 성능 및 한계

- CRA 빌드 특성상 **SSR/SSG 미지원** → 초기 로딩 시 빈 화면 노출(FOUC) 발생
- 이미지 최적화(lazy loading, 반응형 이미지)를 수동으로 처리해야 하는 부담
- SEO 메타데이터가 정적으로 고정되어 콘텐츠별 검색 노출에 불리

→ 이 한계들이 **Next.js로의 마이그레이션을 계획하게 된 직접적인 이유**입니다.

## 💬 회고

이 프로젝트는 외부 API를 다루는 프론트엔드 애플리케이션에서

- API 키를 어떻게 안전하게 다룰 것인가
- 목록 → 상세 → 재생으로 이어지는 UX 흐름을 어떻게 자연스럽게 설계할 것인가
- 서드파티 라이브러리에 의존하는 컴포넌트를 어떻게 재사용 가능하게 캡슐화할 것인가

를 고민하며 만든 결과물입니다.

다만 CRA 기반 구조에서 오는 **SSR 부재, 프록시의 배포 한계, 스타일링 전략 혼재**는 명확한 개선 포인트로 남았고, 이는 현재 진행 중인 **Next.js 리팩토링 프로젝트**로 이어지고 있습니다.
